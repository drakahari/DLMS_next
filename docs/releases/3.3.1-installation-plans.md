These are preparation plans. No installed application or production service may
be changed under candidate-build authority. A later owner approval must name the
exact payload/checksum, destination and stopped-state operation.

Read-only audit identified `linux-330-combined-20261019`, embedded source
`5e5fa245ffb23617890d237c1d6c02a67ff093b1`, through the existing launcher/current
pointer. Re-identify those immediately before any later approved operation.

1. Confirm the existing managed install manifest, current target, launcher,
   exact profile/root and compatibility contract without inspecting study data.
2. Close normally and verify owned backend/helpers and writers are stopped.
   Pending immutable operations or recovery evidence must be resolved through
   supported workflows; never discard them to make an update proceed.
3. Create and verify a full portable backup plus a stopped-state recovery copy
   outside the live root. Record hashes, source schema and restoration procedure.
   Preserve management receipts, launcher/configuration and old payload inventories.
4. Stage the new **managed one-folder** candidate with the established bundled
   manual manager, verify its manifest/compatibility and new payload inventory.
   The standalone AppImage's default namespace is different and is not a drop-in
   replacement. Do not manually point editions at the same live data directory.
5. After separate approval, activate only through the reviewed guarded procedure.
   Reopen the same profile/storage/launcher identity and verify focused workflows.
   Keep all earlier payloads and the pre-update recovery copy.

No schema transition is expected (12→12). Binary rollback still requires clean
shutdown and compatible data/journal state; it cannot undo later writes. If data
must be restored, retain the post-update root separately, then restore a verified
pre-update snapshot with the matching old application in a separate supported
root. An older backup omits subsequent changes throughout the profile.
