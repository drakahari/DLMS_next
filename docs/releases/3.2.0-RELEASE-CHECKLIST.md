# DLMS 3.2.0 final release checklist

This is the execution checklist after source review, not a record of a published
release. The release-preparation task performs no commit, push, merge, tag, or
GitHub Release publication. [Release notes](3.2.0.md) are ready for the release
body; [readiness evidence](3.2.0-READINESS.md) records the host-side audit.

## Final artifact rule

**Every final public native package must be rebuilt from the FINAL FROZEN 3.2.0
RELEASE COMMIT.** Earlier 3.2.0 binaries/packages and their hashes are not final,
even when their embedded version is already 3.2.0. Application changes since
earlier builds include the Content Packs summary-card CSS fix. Do not rename an
old binary, reuse its hash, or package it again as the final build.

Each target machine creates and tests its own final user-facing archive. Fedora
must not repackage Windows, macOS, or another Linux target for this release. The
assembly host receives unchanged final archives and verifies their native-host
hashes. The legacy coordinated packager is not the final workflow for this pass.

## Ordered release gates

1. Review the final source/docs diff; confirm `APP_VERSION = "3.2.0"`, manual
   links, release notes, synthetic fixtures, and clean test results. Markdown is
   the canonical manual; PDF generation is not a gate.
2. Review and create the final commit on `develop/3.2.0` after this preparation
   pass. Include only intended source, docs, and tracked screenshot/thumbnail
   assets, never local packages or video/audio output.
3. Push that reviewed develop commit using the owner's normal workflow.
4. Merge/finalize `main` through the repository's normal review process. The
   repository does not prescribe a merge strategy; any merge resolution that
   changes code requires renewed relevant validation.
5. Record the **full SHA of the final release commit on main** after integration.
   This may differ from the develop commit SHA. Freeze the source; every builder
   checks out that exact SHA in a clean checkout, verifies `git rev-parse HEAD`,
   and checks `git status --porcelain` is empty before building. Record the tree
   hash too (`git rev-parse HEAD^{tree}`). Any source change invalidates this
   freeze and requires rebuilds from the replacement release commit.
6. On each of the six native systems, create the locked environment, prepare the
   native OCR bundle, and build the strict frozen OCR probe using the commands
   below. Record OS/architecture, Python/build-tool versions, and bundle origin.
7. Run the frozen OCR probe successfully, then build the application with
   `DLMS.spec`. Run screenshot OCR and scanned-PDF OCR on a clean native runtime
   without system Tesseract. Confirm timeout/cancellation and bundled discovery.
8. Stage and verify the native input with `verify_release_artifact.py --smoke`;
   perform desktop UAT (launch, Study/Exam, data directory, Shutdown, restart).
9. **On that same native host**, create the final package with single-target
   `package_release.py --smoke`. Do not construct another ZIP/tarball by hand.
10. Verify the exact final package, including clean extraction and native smoke,
    and compare both support documents with the sources in the frozen checkout.
11. Record the final archive SHA-256 printed by the packager; recompute it using
    the native checksum command. Do not substitute the intermediate binary hash.
12. Transfer the six completed archives unchanged, compare each digest with its
    native record, generate `SHA256SUMS.txt`, and run complete-set verification.
    Fill the evidence table below. No target is complete based on another host.
13. Only after these gates pass, create the release tag **v3.2.0** pointing at the
    recorded release commit, following the existing `v3.1.0` tag convention.
    Verify tag-to-commit identity before pushing the tag.
14. Create the GitHub Release for that tag using [3.2.0.md](3.2.0.md). The manual
    URL in those notes intentionally targets `blob/v3.2.0`; it becomes live only
    after the tag is pushed. Confirm it resolves before publication.
15. Upload the six exact native packages and `SHA256SUMS.txt`. Do not upload
    intermediate binaries, build folders, manual source archives, or MP4s.
16. Verify the release notes, tagged Markdown manual, published YouTube overview,
    README paths, and platform availability match the actual assets. The video
    remains hosted at <https://www.youtube.com/watch?v=nrUz3umt8vk>.
17. Download every published archive and checksum manifest once; verify the bytes
    against the native and pre-upload hashes.
18. Check the public download/onboarding path and note the result. Identical
    downloaded bytes do not require repeating all native smoke tests; a checksum
    mismatch stops distribution and requires investigation.

## Canonical matrix

`tools/package_release.py` defines these six targets. All use
`python -m PyInstaller --clean --noconfirm DLMS.spec` after the frozen OCR probe.
The command groups below are run independently on the named system.
Run commands in order and stop on any failure. In PowerShell, check
`$LASTEXITCODE` after each native/Python command before continuing; a later
successful command must not conceal a failed probe or verification.

| Native host | Package target | Artifact-verifier target | Native input under `releases/` | Final archive under `build/release-packages/3.2.0/` |
|---|---|---|---|---|
| Fedora 44 x86_64 | `fedora44-x86_64` | `linux-x86_64` | `DLMS-3.2.0-fedora44-x86_64` | `DLMS-3.2.0-fedora44-x86_64.tar.gz` |
| Ubuntu 24.04 x86_64 | `ubuntu24.04-x86_64` | `linux-x86_64` | `DLMS-3.2.0-ubuntu24.04-x86_64` | `DLMS-3.2.0-ubuntu24.04-x86_64.tar.gz` |
| Ubuntu 26.04 x86_64 | `ubuntu26.04-x86_64` | `linux-x86_64` | `DLMS-3.2.0-ubuntu26.04-x86_64` | `DLMS-3.2.0-ubuntu26.04-x86_64.tar.gz` |
| Omarchy Quattro x86_64 | `omarchy-quattro-x86_64` | `linux-x86_64` | `DLMS-3.2.0-omarchy-quattro-x86_64` | `DLMS-3.2.0-omarchy-quattro-x86_64.tar.gz` |
| Windows 11 x86_64 | `windows11-x86_64` | `windows-x86_64` | `DLMS-3.2.0-windows11-x86_64.exe` | `DLMS-3.2.0-windows11-x86_64.zip` |

does not prove distro identity: the builder must record the named distribution.

## Locked build environment and checks

Use native 64-bit Python (the current validated environment is Python 3.14).
Run from the exact frozen checkout. Create a fresh venv, then activate
`.venv-build/bin/activate` on Linux/macOS or `.venv-build\Scripts\Activate.ps1`
in Windows PowerShell. These commands use `python` from that environment:

```text
python -m venv .venv-build
```

After activation:

```text
python -m pip install -r requirements-build.txt -r requirements-test.txt
python -m pip check
python -m pytest -q -p no:cacheprovider -m "not browser"
python -m unittest discover -s tests -q
python -m compileall -q app.py dlms tools
git diff --check
git rev-parse HEAD
git status --porcelain
```

Use a fresh staging/output directory for the final commit, without old packages.
`releases/`, `build/`, and `.ocr-bundle/` are ignored. `release-packages/` at the
repository root is not globally ignored, so this checklist deliberately puts
final archives under `build/release-packages/3.2.0/`.

## Linux — run once on each named distribution

Install native Tesseract 5 plus English data as documented in
[OCR packaging](../OCR_PACKAGING.md#prepare-the-native-bundle): Fedora uses
`tesseract tesseract-langpack-eng`; Ubuntu uses `tesseract-ocr tesseract-ocr-eng`;
Omarchy uses `tesseract tesseract-data-eng`.

In the activated environment, prepare a new bundle:

```bash
python tools/prepare_ocr_bundle.py
```

On Omarchy use `python tools/prepare_ocr_bundle.py --download-missing-licenses`
instead. For an existing target-native bundle, run
`python tools/prepare_ocr_bundle.py --output .ocr-bundle --validate-only` and
record its provenance; the helper refuses to overwrite an existing bundle.

```bash
export DLMS_TESSERACT_BUNDLE_ROOT="$PWD/.ocr-bundle"
python -m PyInstaller --clean --noconfirm DLMS-OCR-Probe.spec
./dist/DLMS-OCR-Probe
python -m PyInstaller --clean --noconfirm DLMS.spec
mkdir -p releases
```

Choose exactly one line for the host, then run the common block:

```bash
DLMS_TARGET=fedora44-x86_64
# Ubuntu 24.04: DLMS_TARGET=ubuntu24.04-x86_64
# Ubuntu 26.04: DLMS_TARGET=ubuntu26.04-x86_64
# Omarchy Quattro: DLMS_TARGET=omarchy-quattro-x86_64
```

```bash
cp dist/DLMS "releases/DLMS-3.2.0-$DLMS_TARGET"
chmod +x "releases/DLMS-3.2.0-$DLMS_TARGET"
python tools/verify_release_artifact.py linux-x86_64 "releases/DLMS-3.2.0-$DLMS_TARGET" --smoke
python tools/package_release.py --target "$DLMS_TARGET" --artifact "releases/DLMS-3.2.0-$DLMS_TARGET" --output-dir build/release-packages/3.2.0 --smoke
python tools/verify_release_package.py "build/release-packages/3.2.0/DLMS-3.2.0-$DLMS_TARGET.tar.gz" --smoke
sha256sum "build/release-packages/3.2.0/DLMS-3.2.0-$DLMS_TARGET.tar.gz"
```

## Windows 11 x86_64 — native PowerShell

Prepare a trusted Windows Tesseract bundle with explicit source/license paths
using [OCR packaging](../OCR_PACKAGING.md#prepare-the-native-bundle), or validate
the known-good Windows bundle. Do not copy a Linux/macOS bundle.

```powershell
python tools\prepare_ocr_bundle.py --output .ocr-bundle --validate-only
$env:DLMS_TESSERACT_BUNDLE_ROOT = (Resolve-Path .ocr-bundle).Path
python -m PyInstaller --clean --noconfirm DLMS-OCR-Probe.spec
.\dist\DLMS-OCR-Probe.exe
python -m PyInstaller --clean --noconfirm DLMS.spec
New-Item -ItemType Directory -Force releases | Out-Null
Copy-Item dist\DLMS.exe releases\DLMS-3.2.0-windows11-x86_64.exe
python tools\verify_release_artifact.py windows-x86_64 releases\DLMS-3.2.0-windows11-x86_64.exe --smoke
python tools\package_release.py --target windows11-x86_64 --artifact releases\DLMS-3.2.0-windows11-x86_64.exe --output-dir build\release-packages\3.2.0 --smoke
python tools\verify_release_package.py build\release-packages\3.2.0\DLMS-3.2.0-windows11-x86_64.zip --smoke
Get-FileHash build\release-packages\3.2.0\DLMS-3.2.0-windows11-x86_64.zip -Algorithm SHA256
```

## macOS arm64 — native Apple Silicon

Prepare the Homebrew Tesseract bundle on the Mac; the license-download flag is
explicit because Homebrew may omit a required license file. Validate an existing
bundle instead of overwriting it.

```bash
python -c "import platform; assert platform.machine() == 'arm64', platform.machine()"
python tools/prepare_ocr_bundle.py --download-missing-licenses
export DLMS_TESSERACT_BUNDLE_ROOT="$PWD/.ocr-bundle"
python -m PyInstaller --clean --noconfirm DLMS-OCR-Probe.spec
./dist/DLMS-OCR-Probe
python -m PyInstaller --clean --noconfirm DLMS.spec
mkdir -p releases
ditto -c -k --sequesterRsrc --keepParent dist/DLMS.app releases/DLMS-3.2.0-macos-arm64.zip
python tools/verify_release_artifact.py macos-arm64 releases/DLMS-3.2.0-macos-arm64.zip --smoke
python tools/package_release.py --target macos-arm64 --artifact releases/DLMS-3.2.0-macos-arm64.zip --output-dir build/release-packages/3.2.0 --smoke
python tools/verify_release_package.py build/release-packages/3.2.0/DLMS-3.2.0-macos-arm64.zip --smoke
shasum -a 256 build/release-packages/3.2.0/DLMS-3.2.0-macos-arm64.zip
```

The final ZIP must keep **`DLMS.app`, `README.txt`, and `sample_quiz.txt` directly
at the root** (plus allowed macOS metadata), with no versioned wrapper directory.
The packager appends the support files to the verified `ditto` ZIP without
extracting/recreating the app. Native smoke extracts with `ditto` to preserve
framework symlinks and metadata. Preserve that workflow.

## Native UAT and OCR acceptance on every target

- Use a disposable data root or explicit backup; never overwrite live study data
  to run a release test. Verifier smoke already creates an isolated root.
- Launch normally from the desktop/Explorer/Finder, check browser launch, Help,
  Settings, Library, platform data-directory behavior, Shutdown, and restart.
- Import `release_assets/sample_quiz.txt`; exercise Study and Exam, timing/Pause,
  matching/hotspot, Learning Scope, generated Finish Review, and pack report UI.
- Prove screenshot OCR and scanned-PDF OCR from the final packaged runtime on a
  machine without system Tesseract. The probe proves bundled runtime behavior,
  not the whole application's OCR workflow. Missing bundle/files/licenses,
  a failed smoke, or unavailable required OCR blocks that target's publication.
- Inspect Windows/macOS unsigned-app launch prompts according to the manual.
- Confirm backup/restore with synthetic data. Verify the package contains only
  its documented payload and authoritative support documents.

## Assemble unchanged packages and checksums

Collect the six native-produced files into `build/release-packages/3.2.0/` on
the assembly host. Compare their hashes with each native-host record first.

```bash
DLMS_PACKAGE_DIR="$PWD/build/release-packages/3.2.0"
python tools/generate_sha256sums.py --output "$DLMS_PACKAGE_DIR/SHA256SUMS.txt" \
  "$DLMS_PACKAGE_DIR/DLMS-3.2.0-fedora44-x86_64.tar.gz" \
  "$DLMS_PACKAGE_DIR/DLMS-3.2.0-ubuntu24.04-x86_64.tar.gz" \
  "$DLMS_PACKAGE_DIR/DLMS-3.2.0-ubuntu26.04-x86_64.tar.gz" \
  "$DLMS_PACKAGE_DIR/DLMS-3.2.0-omarchy-quattro-x86_64.tar.gz" \
  "$DLMS_PACKAGE_DIR/DLMS-3.2.0-windows11-x86_64.zip" \
  "$DLMS_PACKAGE_DIR/DLMS-3.2.0-macos-arm64.zip"
python tools/verify_release_package.py --complete-set --checksums "$DLMS_PACKAGE_DIR/SHA256SUMS.txt" \
  "$DLMS_PACKAGE_DIR/DLMS-3.2.0-fedora44-x86_64.tar.gz" \
  "$DLMS_PACKAGE_DIR/DLMS-3.2.0-ubuntu24.04-x86_64.tar.gz" \
  "$DLMS_PACKAGE_DIR/DLMS-3.2.0-ubuntu26.04-x86_64.tar.gz" \
  "$DLMS_PACKAGE_DIR/DLMS-3.2.0-omarchy-quattro-x86_64.tar.gz" \
  "$DLMS_PACKAGE_DIR/DLMS-3.2.0-windows11-x86_64.zip" \
  "$DLMS_PACKAGE_DIR/DLMS-3.2.0-macos-arm64.zip"
(cd "$DLMS_PACKAGE_DIR" && sha256sum --check SHA256SUMS.txt)
```

This is structural/checksum assembly validation, not cross-platform native UAT.
Upload exactly the six archives plus `SHA256SUMS.txt`; GitHub supplies source
archives automatically. YouTube hosts the overview; the lossless master remains
local/archival. A downloadable video release asset is optional and separate.
